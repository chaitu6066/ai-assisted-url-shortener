# Database Design

## Project

AI-Assisted Production-Grade URL Shortener

## 1. Purpose

This document defines the PostgreSQL data model, constraints, indexes, transaction boundaries, and concurrency-safe SQL operations for the URL Shortener prototype.

The design prioritizes:

- correctness under concurrent requests;
- fast redirect lookups;
- database-enforced short-code uniqueness;
- minimal write-path complexity;
- portability across multiple stateless application instances;
- clear evolution options for higher scale.

---

## 2. Selected Database

### PostgreSQL

PostgreSQL is selected because the prototype requires:

- ACID transactions;
- unique constraints;
- indexed short-code lookup;
- atomic counter updates;
- `INSERT ... ON CONFLICT`;
- `UPDATE ... RETURNING`;
- mature Spring Boot integration.

PostgreSQL is the system of record. A cache may be added later, but it must not replace durable persistence as the authoritative source.

---

## 3. Data Model

The prototype requires one primary table:

```text
url_mapping
```

It stores:

- the public short code;
- the original destination URL;
- creation metadata;
- aggregate click analytics.

A separate analytics table is not required for the current aggregate-only requirement.

---

## 4. Table Definition

```sql
CREATE TABLE url_mapping (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    short_code VARCHAR(32) NOT NULL,
    original_url VARCHAR(2048) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_accessed_at TIMESTAMPTZ NULL,
    click_count BIGINT NOT NULL DEFAULT 0,

    CONSTRAINT uk_url_mapping_short_code UNIQUE (short_code),
    CONSTRAINT ck_url_mapping_short_code_length
        CHECK (char_length(short_code) BETWEEN 3 AND 32),
    CONSTRAINT ck_url_mapping_short_code_characters
        CHECK (short_code ~ '^[A-Za-z0-9][A-Za-z0-9-]*[A-Za-z0-9]$'),
    CONSTRAINT ck_url_mapping_click_count_non_negative
        CHECK (click_count >= 0)
);
```

## Column definitions

| Column | Type | Null? | Purpose |
|---|---|---:|---|
| `id` | `BIGINT IDENTITY` | No | Internal database identifier |
| `short_code` | `VARCHAR(32)` | No | Generated 10-character Base62 code or 3–32 character custom alias |
| `original_url` | `VARCHAR(2048)` | No | Destination URL |
| `created_at` | `TIMESTAMPTZ` | No | Creation time using the database clock |
| `last_accessed_at` | `TIMESTAMPTZ` | Yes | Time of the most recent recorded redirect |
| `click_count` | `BIGINT` | No | Total number of recorded redirects |

---

## 5. Why Use an Internal Numeric Primary Key?

The public short code is unique, so it could technically be the primary key. The selected design uses a numeric surrogate key and keeps `short_code` as a unique alternate key.

Reasons:

- the public identifier and internal database identity remain separate;
- future child tables can reference a compact numeric key;
- a future alias-change feature would not require changing foreign keys;
- numeric primary keys are smaller and efficient for internal joins;
- the API never exposes or depends on the internal ID.

The identity sequence may contain gaps after rollbacks or conflicts. That is acceptable because the ID has no business meaning.

---

## 6. Why `VARCHAR(32)` for `short_code`?

Two identifier types share the column:

- generated code: exactly 10 Base62 characters;
- custom alias: 3–32 lowercase letters, digits, or hyphens.

The database constraint permits the combined safe character set. The application applies the stricter rule:

- generated codes: `[A-Za-z0-9]{10}`;
- custom aliases: lowercase letters, digits, and hyphens.

Reserved aliases are validated in the application because that list is configuration and may evolve without a schema migration.

---

## 7. Why `VARCHAR(2048)` for the Original URL?

The API sets a 2048-character maximum. The database applies the same boundary so invalid oversized data cannot be persisted through another code path.

The database does not attempt full URL validation. URL parsing, allowed schemes, host validation, embedded-credential rejection, and control-character validation belong in the application layer.

---

## 8. Timestamp Strategy

The table uses:

```sql
TIMESTAMPTZ
```

and database-generated timestamps:

```sql
CURRENT_TIMESTAMP
```

Reasons:

- `TIMESTAMPTZ` represents an absolute instant;
- database time remains consistent across multiple application pods;
- application-server timezone differences do not affect stored values;
- API responses can convert the instant to ISO-8601 UTC.

The database session should use UTC where possible, and the API shall return timestamps with a UTC `Z` suffix.

---

## 9. Index Strategy

The unique constraint creates a B-tree unique index on:

```text
short_code
```

This index supports:

- redirect lookup;
- analytics lookup;
- duplicate custom-alias detection;
- generated-code collision detection.

### Deliberately omitted indexes

No index is initially created on:

- `original_url`;
- `created_at`;
- `last_accessed_at`;
- `click_count`.

Reasons:

- the prototype does not search or deduplicate by original URL;
- it does not expose list, reporting, or date-range queries;
- unnecessary indexes increase storage and write cost.

Indexes should be added in response to real query patterns and measured execution plans.

## 10. Concurrency-Safe Insert

## 10.1 Preferred SQL

```sql
INSERT INTO url_mapping (
    short_code,
    original_url
)
VALUES (
    :shortCode,
    :originalUrl
)
ON CONFLICT (short_code) DO NOTHING
RETURNING
    id,
    short_code,
    original_url,
    created_at,
    last_accessed_at,
    click_count;
```

### Result interpretation

- One row returned: insert succeeded.
- No row returned: the short code already exists.

This avoids a separate `SELECT exists` query and avoids using a Java exception as normal collision control flow.

---

## 10.2 Automatically generated code flow

```text
Generate candidate code
        ↓
Attempt INSERT ... ON CONFLICT DO NOTHING
        ↓
Row returned?
   ├── Yes → creation succeeds
   └── No  → generate another code and retry immediately
```

The retry is bounded by configuration, for example:

```text
maximum attempts = 5
```

There is no intentional sleep between retries.

---

## 10.3 Custom alias flow

For a user-provided alias:

```text
Attempt atomic insert
        ↓
Row returned?
   ├── Yes → return 201 Created
   └── No  → return 409 Conflict
```

The application must not replace the requested alias with a generated value.

---

## 10.4 Why not check first and insert later?

This flow is unsafe:

```text
SELECT whether code exists
        ↓
INSERT if absent
```

Two concurrent requests can both observe that the code is absent and then race to insert it.

The database unique constraint and atomic insert are the final concurrency controls across:

- threads;
- JVMs;
- servers;
- Kubernetes pods.

---

## 11. Redirect and Atomic Analytics Update

The redirect path is expected to be the most frequently executed operation.

### Selected SQL

```sql
UPDATE url_mapping
SET
    click_count = click_count + 1,
    last_accessed_at = CURRENT_TIMESTAMP
WHERE short_code = :shortCode
RETURNING original_url;
```

### Behavior

- One row returned: mapping exists, analytics were atomically updated, and the returned URL is used for the HTTP redirect.
- No row returned: mapping does not exist, so the API returns `404 Not Found`.

### Why combine lookup and analytics update?

This design:

- performs one database round trip rather than a select followed by an update;
- prevents lost click increments;
- returns the destination from the same atomic statement;
- behaves correctly under concurrent requests.

This refines the earlier conceptual architecture that showed separate lookup and update operations. The implementation uses one database statement for stronger correctness and lower redirect-path latency.

---

## 12. Analytics Read Query

```sql
SELECT
    short_code,
    original_url,
    created_at,
    last_accessed_at,
    click_count
FROM url_mapping
WHERE short_code = :shortCode;
```

The unique short-code index supports the lookup.

The API constructs `shortUrl` using the configured public base URL; it is not stored in the database.

---

## 13. Transaction Design

Each core operation is intentionally small.

### Create URL

A single atomic insert statement forms the transaction boundary.

### Redirect

A single atomic `UPDATE ... RETURNING` statement forms the transaction boundary.

### Analytics query

A single indexed read is sufficient.

### Isolation level

PostgreSQL's default `READ COMMITTED` isolation level is sufficient because:

- uniqueness is protected by a database constraint;
- click increments are atomic;
- no multi-statement read-modify-write transaction is used;
- serializable isolation would add unnecessary contention.

---

## 14. Spring Persistence Approach

### Recommended implementation

Use:

- Spring Data JPA for the entity and straightforward read operations;
- `NamedParameterJdbcTemplate` or a custom repository adapter for PostgreSQL-specific atomic statements:
  - `INSERT ... ON CONFLICT ... RETURNING`;
  - `UPDATE ... RETURNING`.

### Why combine JPA and JDBC?

JPA is convenient for ordinary entity mapping and reads, while the two concurrency-sensitive operations are clearer and more efficient as explicit SQL.

This is not a general rule to bypass JPA. It is a targeted decision for operations where PostgreSQL provides useful atomic semantics.

### Alternative considered

`saveAndFlush()` with `DataIntegrityViolationException` and a new transaction per retry is valid, but it uses exception-driven collision handling and makes retry transaction boundaries more subtle.

---

## 15. Schema Migration Strategy

Use Flyway for version-controlled database migrations.

Expected file:

```text
src/main/resources/db/migration/V1__create_url_mapping.sql
```

### Spring/JPA configuration

For the non-test profile:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Hibernate validates entity-to-schema compatibility but does not create or mutate production tables.

### Why not `ddl-auto=create` or `update`?

- schema changes would not be explicitly reviewed;
- behavior may differ across environments;
- destructive or unintended changes are possible;
- migration history would be missing.

Flyway provides a repeatable, auditable database-change process.

## 16. Entity Mapping

Conceptual Java entity:

```java
@Entity
@Table(
    name = "url_mapping",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_url_mapping_short_code",
            columnNames = "short_code"
        )
    }
)
public class UrlMapping {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "short_code", nullable = false, length = 32)
    private String shortCode;

    @Column(name = "original_url", nullable = false, length = 2048)
    private String originalUrl;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "last_accessed_at")
    private Instant lastAccessedAt;

    @Column(name = "click_count", nullable = false)
    private long clickCount;
}
```

The exact implementation may use a constructor or factory method and should avoid public setters for fields controlled by persistence or business rules.

---

## 17. Why No Unique Constraint on `original_url`?

The same destination may need multiple short links for:

- separate campaigns;
- separate users;
- separate analytics;
- future expiry policies;
- different custom aliases.

Therefore:

```text
original_url
```

is deliberately not unique.

Deduplication would be a different business rule and should not be introduced implicitly through the schema.

---

## 18. Why Keep Aggregate Analytics in the Same Table?

The requirement asks only for:

- total click count;
- creation time;
- last-accessed time.

Keeping these values in `url_mapping`:

- avoids a join;
- simplifies the analytics response;
- supports an atomic redirect update;
- avoids one event row per click.

### Future evolution

If the product later requires:

- clicks by hour or day;
- geography;
- referrer;
- device;
- campaign attribution;

clicks should be emitted as events and processed into a separate analytics store.

---

## 19. Data Retention and Deletion

The prototype does not implement deletion or expiry.

Consequences:

- mappings remain active indefinitely;
- aliases are not reused;
- analytics are retained with the mapping.

Future deletion requires explicit decisions about:

- soft versus hard delete;
- alias reuse;
- historical analytics;
- audit requirements;
- legal retention;
- cache invalidation.

---

## 20. Database Failure Behavior

### Creation failure

If PostgreSQL is unavailable, the mapping cannot be durably created. Return a controlled `503 Service Unavailable`.

### Redirect failure

PostgreSQL is required to resolve the destination in the prototype. If it is unavailable, return a controlled service error.

### Future resilience

A read-through cache could allow popular redirects during partial database outages, but creation would still require durable persistence.

## 21. Database Validation Test Matrix

| Test | Expected Result |
|---|---|
| Apply `V1` migration to an empty database | Table and constraints created |
| Insert valid generated code | Row created |
| Insert valid custom alias | Row created |
| Insert duplicate short code | No second row created |
| Concurrent requests for same custom alias | Exactly one succeeds |
| Force first generated-code collision | Next candidate is inserted |
| Exhaust generated-code retries | Service returns controlled allocation failure |
| Redirect existing code | Count incremented, timestamp updated, URL returned |
| Concurrent redirects | No lost count increments |
| Redirect unknown code | No row returned |
| Insert negative click count directly | Database rejects row |
| Insert invalid short-code length | Database rejects row |
| Restart application | Existing mappings remain available |
| JPA validation against migration | Startup succeeds when models match |

## 22. Future Database Evolution

Potential future changes:

- `expires_at TIMESTAMPTZ`;
- `status` such as active, disabled, or expired;
- `owner_id`;
- `custom_domain_id`;
- separate click-event pipeline;
- read replicas;
- partitioning;
- sharding by short-code hash;
- archival and retention jobs;
- administrative takedown metadata.

These changes should be introduced through new Flyway migrations rather than editing the original migration after it has been applied.

---

## 23. Key Database Decisions

1. PostgreSQL is the durable system of record.
2. Use one `url_mapping` table for the prototype.
3. Use an internal numeric identity primary key.
4. Keep `short_code` unique and indexed.
5. Do not make `original_url` unique.
6. Use `TIMESTAMPTZ` and the database clock.
7. Use atomic `INSERT ... ON CONFLICT ... RETURNING`.
8. Use atomic `UPDATE ... RETURNING` for redirect and analytics.
9. Use default `READ COMMITTED` isolation.
10. Use Flyway migrations and Hibernate schema validation.
11. Avoid unnecessary indexes.
12. Keep aggregate analytics in the same table until richer reporting is required.
